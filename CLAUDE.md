# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

The specification (not an implementation) of the GA4GH Tool Registry Service (TRS) API, a read-only API for discovering tools and workflows (CWL, WDL, Nextflow, Galaxy, Snakemake) and their containers. The deliverable is a single OpenAPI 3 document; there is no application code and no unit tests.

## Where changes go

- `openapi/openapi.yaml` is the only spec to edit. It is the current TRS version (`info.version`, e.g. 2.1.0), served under `/ga4gh/trs/v2`. The TRS validation server also uses this file.
- Leave `openapi/v1/` and `openapi/v2/` alone. They are frozen historical copies kept for backward compatibility.
- The `TRSService` and `ServiceType` schemas are pulled in through remote `$ref`s to the GA4GH service-info spec (v1.0.0). Validation and bundling therefore need network access.
- `registry.json` lists the service-info URLs of public TRS registries. New registries are added by PR.
- TRS follows semantic versioning (see `CONTRIBUTING.md`). Decide whether a change is major, minor or patch, and bump `info.version` to match when appropriate.

## Commands

```bash
npm ci                                  # install doc tooling (@ga4gh/gh-openapi-docs, redocly, redoc-cli)
npx gh-openapi-docs                     # build the docs preview from openapi/openapi.yaml (config: .spec-docs.json)
npx @redocly/openapi-cli lint openapi/openapi.yaml   # local lint (not run in CI)
```

CI runs on every push (`.github/workflows/`):
- `validate.yaml` validates `openapi/openapi.yaml` against a self-hosted Swagger Editor v4 container. It uses v4 because `swagger-editor-validate` does not support editor v5.
- `main.yml` runs `markdown-link-check -c .github/workflows/mlc_config.json ./README.md`, then builds the docs with `gh-openapi-docs` and publishes them to `gh-pages` under `preview/<branch>/` using `scripts/update-ghpages.sh`.

Some files are legacy leftovers from the Travis/Swagger 2 era and are not used by CI: `build.gradle` (it points at a non-existent `openapi/ga4gh-tool-discovery.yaml`), `src/asciidoc/`, `scripts/buildui.js` and `scripts/openAPI3.sh`.

## Branching

The repo follows HubFlow (GitFlow) conventions:
- `master` holds the last production release.
- `develop` is the main integration branch and the default target for PRs.
- New work happens on `feature/*` branches, which are created from `develop` and merged back into it.
- `hotfix/*` branches are for urgent fixes, and `release/*` branches are cut for releases.

## Pull requests

Always create PRs in draft mode. A human developer must be the one to mark a PR ready for review. Claude Code should not take it out of draft itself.

Always check with the user before pushing to GitHub. This applies even to a branch or PR already being worked on in the conversation, because a push starts CI and republishes the `gh-pages` preview.

When a GitHub MCP server or `gh` is available, diff the current work against `develop` (or whatever branch the PR targets). Keep stylistic and other minor changes to a minimum, since they inflate the diff and make it harder to review. Reordering or reformatting YAML in `openapi/openapi.yaml` falls under this.

Keep the "Description" and "Review Instructions" sections brief: one paragraph each, or two for a genuinely complicated change.

### Using CI and review feedback to guide work

When diagnosing a failing build or iterating on an open PR, use the signals that are actually available instead of guessing:
- If `gh` or a GitHub MCP server is available, use GitHub Actions results (check runs and job logs) to guide diagnosis and fixes.
- Treat code review comments from human developers as high-priority direction. Investigate each one and propose concrete solutions, even without being asked to. Comments from bots (such as Copilot Autofix) are useful, but they come second to human reviewers.
